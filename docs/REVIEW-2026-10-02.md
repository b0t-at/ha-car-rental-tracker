# Code Review Report: 2026-10-02

Scope: the whole repository at `dec4d52` (v1.3.0). That covers the integration (`__init__.py`, `sensor.py`, `config_flow.py`, `calculations.py`, `const.py`, manifest and translations), the Lovelace card, the docs and CI.

Method:

1. Five parallel reviewers each covered one area: lifecycle/async, calculations, sensors and config flow, frontend card, docs and CI.
2. An independent skeptic tried to refute each finding. 66 of 68 survived; 2 were refuted.
3. A completeness critic then found 7 more issues.
4. Fixes were made on branch `fix/review-findings` in four tracks with separate files, then went through two rounds of multi-lens review and fixing.

Some findings overlap because reviewers in different areas reported the same root cause.

## Most important bugs

| # | Severity | Issue | Fix |
|---|----------|-------|-----|
| 1 | High | **The coordinator was never torn down.** Every reload, including the one each options save triggers, left a zombie coordinator with the old config. It kept its state listener and its 5-minute timer, ran recorder queries and wrote to removed entities. Entity listeners were never removed either. | The coordinator is now a `DataUpdateCoordinator` in `entry.runtime_data`, and the entities are `CoordinatorEntity`. The state listener is registered with `entry.async_on_unload`. |
| 2 | High | **The monthly baseline broke after a recorder purge.** By default the recorder keeps 10 days. From roughly the 11th of each month, the month-start reading was gone, so "Monthly Driven" silently used a mid-month reading and under-reported. | The baseline is selected in the new HA-free `baseline.py`, using a reading at or before midnight on the 1st, or at most 24 h after it. It is cached per month and saved in `.storage/car_rental_tracker.<entry_id>`. A rollover while HA is running is captured from the coordinator's own readings. |
| 3 | High | **The card picked the wrong car.** Its sensor lookup built a prefix that never matched, then fell back to a global substring search. With several rentals, it could show another contract's numbers. | The card resolves sibling sensors through `hass.entities[entity].device_id` plus `translation_key`, and falls back to matching the entity-id suffix. |
| 4 | Medium | **The total allowance treated the end date as exclusive** while `days_total` treated it as inclusive. A Jan 1 – Dec 31 contract gave 11.97 months, and the fractional month could *decrease* as the end date moved later. | The end date is inclusive everywhere, and the fraction is measured against the month the partial period actually falls in. It is now strictly monotonic, which a test checks over 3,200 dates. |
| 5 | Medium | **Before the contract started**, days elapsed and time progress went negative and the status showed a false "warning". | Values are clamped: elapsed 0, progress 0, status ok. |
| 6 | Medium | **The recorder was queried on every update**: every 5 minutes and on every odometer change, over a 35-day window. | The baseline is cached per month. An estimate is retried hourly only while it can still improve. |
| 7 | Medium | **The card was never actually registered**, although the docs said it was auto-registered. | It is now loaded with `frontend.add_extra_js_url` and removed when the last entry is deleted. A `customElements.get` guard keeps a leftover manual resource harmless. |
| 8 | Medium | **The card's monthly allowance was computed as driven + remaining**, which is wrong once over the limit. Unavailable values showed as `NaN` and counted as healthy. | A new **Monthly Allowance** sensor provides the value. Unavailable values now show "—" with neutral styling. |
| 9 | Medium | The options flow threw away user input on a validation error. The default end date equalled the start date, so submitting the defaults always failed. The odometer entity was not validated. | Input is kept on error. The default end date is start + 1 year − 1 day. The flows check that the entity exists and is numeric. |
| 10 | Medium | The docs were wrong in many places: entity ids, a non-existent sensor, rental-month vs calendar-month semantics, a monthly-summary automation that fired daily, a non-existent visual editor and outdated UI paths. Tests never ran in CI. | The docs were rewritten against the code. `docs/SUMMARY.md` (a stale generated report) was removed. A new `tests.yml` CI workflow was added. |

## Other notable changes

- **Timezones:** calculations used `date.today()` (the OS timezone) while the sensors used HA's timezone. `today` is now injected from `dt_util.now()`.
- **Odometer states:** `unavailable` and `unknown` no longer spam warnings. Sensors are `unavailable` until the first valid reading and then keep the last good value.
- **Concurrency:** updates are serialized with an `asyncio.Lock`, and odometer changes are debounced.
- **Sensor metadata:**
  - Every name comes from a translation (`translation_key`).
  - Status is an `ENUM` sensor with translated states.
  - The days sensors use `UnitOfTime.DAYS` with the `DURATION` device class.
  - Projected Cost is `MONETARY` in `hass.config.currency`.
  - KM Allowed uses the `MEASUREMENT` state class.
  - The device is marked as a `SERVICE` device.
- **Config flow:** the options flow keeps `unique_id` and title in sync and rejects collisions. `ConfigFlowResult` is used, and unused imports and constants were removed.
- **Manifest:** `recorder` is now an `after_dependency`. `frontend` was added as a dependency. The documentation URL was fixed. `hacs.json` declares a minimum of **HA 2024.12.0**, which the options-flow `self.config_entry` pattern requires.
- **Card:**
  - The DOM is built once and only updated when relevant states change.
  - All values go through `textContent`, so there is no XSS through `innerHTML`.
  - It uses theme variables, so dark mode works.
  - Progress bars are accessible (`role=progressbar`).
  - Units and currency come from the entities.
  - It has `getStubConfig`, `getGridOptions` and `setConfig` validation.
  - The KM bar colour follows the status sensor.
  - The monthly bar uses the elapsed share of the month, and a contract that has ended counts its month as complete.
- **Tests:** the date-dependent tests in `run_tests.py` with conditional assertions were replaced by 80 deterministic tests in `tests/test_calculations.py` and `tests/test_baseline.py`, plus `tests/conftest.py`.
- **CI:** the validate workflows now run with `contents: read` only.

## Upgrade notes (worth putting in the release notes)

- **Statistics:** sensor metadata changed (days units, the cost and allowance state classes). Users may need to fix statistics issues under Developer Tools → Statistics.
- **Allowance:** the end date is now inclusive. Contracts whose end date was entered as "the day after" will show about one extra day of allowance.
- **Version:** the minimum HA version is now 2024.12.0.
- **Card:** the card loads automatically. A manually added resource can be removed.

## Not changed: recommendations for the maintainer

These are product or semantics decisions, so they were deliberately left out:

1. **Early projection volatility.** The linear projection over the first few days makes the status flip to "warning" after one long drive. A minimum sample before projection-based warnings would help, for example `days_elapsed >= 7`.
2. **Partial first and last months.** Monthly Remaining uses the full monthly allowance even in a partial first or last calendar month. Prorating would match the total allowance, but it changes what users see.
3. **Odometer unit conversion.** A source in miles is only warned about, not converted, because the configured initial odometer and allowance have no unit field.
4. **CHANGELOG noise.** The duplicate entries come from release-please history. Clean them up manually if wanted.
5. **Untested against a real HA instance.** Home Assistant is not installed in the local environment. The Python modules that import HA were checked with `py_compile` and multi-agent review against the HA 2024.12 source, but were never run. Before release, run hassfest/HACS CI and do a manual smoke test in HA (setup, options change and reload, delete the entry, the card on a dashboard).

## Refuted findings

- The status being "critical" at exactly 100 % while `is_over_limit` is false. Judged intended: 100 % used means nothing is left.
- `max(x, 0)` returning int `0`. Harmless, because the value is rounded and serialized the same way.
